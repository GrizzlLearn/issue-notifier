# Issue Notifier

Плагин Jira для уведомлений через **Email, Mattermost и Telegram**. Отправляет изменения полей задачи, упоминания, новые комментарии, назначение исполнителя и переходы в выбранные закрывающие статусы.

Администратор задаёт правила для проектов и категорий. Пользователь выбирает каналы и может делегировать уведомления на время отсутствия. Очередь хранится в БД Jira и продолжает обработку после перезапуска; подтверждённые отправки при повторе пропускаются.

Целевая платформа: **Jira 9.12.2, Java 17**, Atlassian Plugin SDK. Frontend — React 17 и AUI. Совместимость с другими версиями Jira требует отдельной проверки.

## Начало работы

1. Соберите плагин командой `atlas-mvn package` и установите `target/in-<version>.jar` через управление приложениями Jira.
2. Откройте **Управление приложениями → Issue Notifier → Настройки плагина**. Прямой путь относительно Jira: `/plugins/servlet/issue-notifier/admin`.
3. На вкладке **«Каналы»** настройте доставку, выполните проверочную отправку и включите нужные каналы.
4. На вкладке **«Контекст проектов»** при необходимости создайте отдельные правила для проектов и категорий.
5. На вкладке **«Действия»** включите нужные уведомления, выберите получателей, заполните шаблоны и закрывающие статусы. Сохраните изменения.
6. В верхнем меню Jira откройте **«Уведомления»** и настройте собственные каналы доставки.

На новой установке каналы и действия требуют настройки. Рассылка наблюдателям об изменении полей по умолчанию выключена; у нового пользователя каналы не выбраны.

## Настройка каналов

Админка требует глобальное право Jira `ADMINISTER`. Проверочная отправка использует значения из формы, поэтому предварительно сохранять токен не нужно. При включении канала сервер проверяет, что именно эта конфигурация успешно прошла проверку. Уже включённый канал можно редактировать без повторного включения.

### Email

- Настройте исходящий SMTP-сервер штатными средствами Jira и включите отправку почты.
- У получателя должен быть email в профиле Jira.
- В плагине достаточно включить канал Email после успешной проверки.

Успех проверки означает постановку письма в очередь Jira, а не получение письма в ящике. Дальнейшую доставку выполняет Jira. В локальной SDK Jira проверьте флаг `atlassian.mail.senddisabled`, если письма не уходят.

### Mattermost

Укажите URL сервера, ID учётной записи бота и Bearer-токен. Плагин ищет получателя в Mattermost по email из Jira и отправляет сообщение в личный канал с ботом. Учётная запись получателя с таким email должна существовать в Mattermost; бот должен иметь доступ к используемым API.

### Telegram

1. Укажите username и токен бота.
2. Получатель должен начать диалог с ботом и указать свой числовой `chat_id` в настройках «Уведомления» в Jira.
3. Выполните проверку на этого пользователя, включите канал и сохраните настройки.

**Первое включение:** для проверки нужен заранее известный `chat_id`. Пока канал выключен, плагин не опрашивает Telegram и сам не отвечает на `/start`. Для нового бота отправьте ему `/start` из Telegram и получите `message.chat.id` через Bot API `getUpdates`, затем внесите число в настройки пользователя. После включения канала плагин сам отвечает на `/start` значением `chat_id`.

Опрос Telegram выполняется каждые 5 секунд. Offset хранится отдельно для каждого бота. При переходе со старого общего offset возможен повтор ответа на ещё доступную команду `/start`.

### Токены

Сохранённые токены не возвращаются в интерфейс. Метка «Установлен» показывает только наличие значения. Пустое поле оставляет прежний токен; новое значение заменяет его после сохранения. Это write-only поведение API, а не шифрование токенов в хранилище.

## Правила уведомлений

### Контексты проектов

Контекст содержит проекты и категории, включённые действия, источники получателей и закрывающие статусы по проектам.

- Явно выбранный проект имеет приоритет над категорией.
- Если явного проекта нет, используется контекст его категории.
- Остальные задачи обрабатываются встроенным контекстом **«Остальные проекты»**. Его нельзя удалить.
- Настройки разных контекстов не объединяются. Шаблоны сообщений общие на весь инстанс.

При одновременном редактировании сервер отклонит сохранение устаревшего списка контекстов. Правки останутся в форме: перед обновлением страницы сохраните их для сравнения с актуальными данными.

Контексты и прочие настройки сохраняются двумя запросами. Если сохранена только первая часть, интерфейс явно сообщает об этом и оставляет остальные изменения несохранёнными.

### События и получатели

| Уведомление | Кому отправляется |
|---|---|
| Изменение полей | Наблюдателям с учётом личного фильтра проектов |
| Упоминание | Пользователям из упоминаний в новом комментарии |
| Назначение исполнителя | Пользователю, назначенному по changelog события |
| Новый комментарий | Получателям, выбранным для действия в контексте |
| Переход в закрывающий статус | Получателям действия, если новый статус выбран для проекта |

Для настраиваемых получателей доступны автор задачи, создатель, исполнитель, наблюдатели и значения custom user picker-полей. Закрытие определяется выбранными статусами конкретного проекта, а не категорией статуса «Готово».

Рассылка изменений полей включается отдельно от действий. Можно выбрать группы отслеживаемых полей: описание, кастомные и прочие поля. Личный фильтр проектов применяется только к наблюдению за изменениями; область действий задаётся администратором.

Перед доставкой проверяются активность пользователя, его настройки и доступ к задаче. Автор события не уведомляется о своём действии. Упоминание имеет приоритет над обычным уведомлением о комментарии; получатели приоритетных действий исключаются из последующих рассылок того же события.

Создание и удаление задачи сами по себе не рассылаются. Редактирование комментария не считается новым комментарием. Если Jira передала событие с отключённой отправкой уведомлений (`sendMail=false`), плагин его пропускает.

### Комментарии и шаблоны

Администратор выбирает режим текста комментария: всегда скрывать, всегда показывать или дать выбор пользователю. Ограничения видимости имеют приоритет:

- Комментарий с ограничением по группе или роли отправляется без текста и только тем, кто имеет к нему доступ. Учитываются ограничения при создании события и на момент обработки.
- Внутренний комментарий Service Desk направляется только исполнителю, без делегирования.
- Если комментарий удалён, уведомление о нём не отправляется.

Для действий с комментариями предусмотрены два шаблона: обычный и без текста. Заполните оба варианта, если используете разные режимы видимости. Пустой шаблон означает отсутствие отправки по этому каналу.

| Канал | Разметка шаблона |
|---|---|
| Mattermost | Markdown |
| Telegram | HTML, поддерживаемый Telegram |
| Email | HTML; тема письма — обычный текст |

Список допустимых плейсхолдеров показан под действием. Общие: `{issueKey}`, `{issueUrl}`, `{summary}`, `{project}`, `{author}`. В зависимости от действия доступны `{comment}`, `{assignee}` или `{status}`. Неизвестные плейсхолдеры отклоняются при сохранении; подставляемые значения экранируются для канала. Тема Email по умолчанию: `Jira: {issueKey} — {summary}`.

### Личные настройки и делегирование

В меню **«Уведомления»** выберите доступные каналы. Чтобы отказаться от доставки, снимите все каналы. Вкладка «Наблюдение» с выбором проектов появляется, когда администратор включил рассылку изменений полей.

Делегирование перенаправляет уведомления максимум пяти пользователям до выбранной даты или бессрочно. Дата включительная, граница рассчитывается по UTC. Цепочки делегирования не обходятся: применяется только один уровень.

Каналы берутся из настроек итогового получателя. Делегат также должен быть активен, включить уведомления и иметь доступ к задаче и комментарию. Отсутствие подходящего канала или прав у делегата не гарантирует возврата отправки исходному пользователю.

## Очередь и повторные попытки

Снимок события синхронно сохраняется в Active Objects, затем обрабатывается в фоне. Очередь переживает перезапуск Jira; занятость worker не удаляет ожидающие события. Опрос выполняется раз в секунду, первый — через 30 секунд после запуска. На ноде работают четыре worker; кластерные блокировки защищают одно задание от одновременной обработки.

После ошибки событие остаётся в БД. Паузы между попытками: **2, 4, 8, 16, 32, 64, 128, 256 секунд**, далее — каждые **5 минут**. Автоматического удаления после определённого числа ошибок нет.

Каждая успешная отправка подтверждается отдельно для сочетания **действие + получатель + канал**. Например, если Email и Telegram сработали, а Mattermost упал, при повторе подтверждённые Email и Telegram пропускаются. После полного завершения запись события и её журнал удаляются.

Ограничения доставки:

- Между внешней отправкой и сохранением подтверждения остаётся окно: при падении процесса или ошибке БД возможен дубль.
- Для Email подтверждается приём в очередь Jira, а не доставка до ящика.
- При недоступной БД до сохранения события очередь не может его восстановить; listener пишет ошибку в лог. Запись очереди не образует общей транзакции с изменением задачи Jira.
- Права, настройки и получатели проверяются заново при повторе; полный план рассылки не замораживается.
- Старые задания без журнала подтверждений не знают о прежних успешных отправках.
- При длительной недоступности каналов очередь растёт. JSON-журнал переписывается после каждой успешной доставки; сценарий с тысячами доставок на одно событие требует отдельной оценки нагрузки.

## Диагностика

### Вкладка «Ошибки отправки»

Показывает текущие неудачные события, ожидающие повторной обработки: задачу, действие, комментарий или изменённые поля, канал и ключ получателя, причину, число неудачных попыток и время следующего повтора.

1. Найдите задачу и событие, посмотрите столбец «Причина».
2. Исправьте настройки, доступность сервиса или данные получателя.
3. Дождитесь автоматической попытки. Нажмите «Обновить», чтобы получить первую страницу актуального списка; «Назад» и «Далее» переключают страницы.

После успешной обработки событие исчезает. Это список текущих проблем, а не история доставок; Удаление доступно только для событий в карантине. Кнопка «Повторить сейчас» переносит следующую попытку на текущий момент; доставку выполняет обычный обработчик очереди. Подтверждения успешных отправок и счётчик ошибок сохраняются. Для уже обрабатываемого события сервер возвращает конфликт; обновите список и попробуйте снова. Для событий с нечитаемыми метаданными повтор из интерфейса недоступен. Администратор видит сведения только о доступных ему задачах и комментариях. Для старых записей подробности ошибки появятся после следующей попытки.

Сводка не раскрывает токены и содержимое уведомлений. Известные ошибки HTTP, сети и настроек показываются понятным сообщением; для неизвестных причин отображается класс исключения. Одна запись может содержать несколько причин для разных получателей и каналов.

### Логи

Вкладка «Диагностика» управляет подробным логированием по областям. Общий переключатель включает все области. Основной файл: `<jira-home>/log/issue-notifier.log`; WARN и ERROR также направляются в штатный лог Jira.

В локальном SDK окружении смотрите:

```text
target/jira/home/log/issue-notifier.log
target/jira/home/log/atlassian-jira.log
```

Если уведомления не приходят, проверьте по порядку: канал и проверочную отправку; включение действия/наблюдения; контекст и шаблон, включая вариант без текста; личные каналы; делегирование и права; затем вкладку ошибок и логи. Для закрытия дополнительно проверьте статусы проекта, для Telegram — `chat_id`, для Mattermost — совпадение email, для Email — исходящую почту Jira.

## Локальная разработка

Нужны Java 17 и Atlassian Plugin SDK. Maven-команды выполняйте через `atlas-mvn`: обычный `mvn` не использует необходимую конфигурацию SDK для Atlassian-зависимостей. Frontend Maven plugin устанавливает локальный Node.js 20.14.0 и собирает ресурсы.

```bash
# Unit-тесты Java
atlas-mvn test

# Frontend и JAR; QuickReload подхватит JAR, если локальная Jira уже работает
atlas-mvn package

# Запуск локальной Jira — холодный старт может занять около 10 минут
atlas-run

# Запуск с отладкой, порт подключения 5005
atlas-debug
```

Локальная Jira доступна по адресу `http://localhost:2990/jira`.

Команды frontend запускаются из корня репозитория после установки его зависимостей:

```bash
npm install --prefix src/main/frontend
npm test --prefix src/main/frontend
npm run lint --prefix src/main/frontend
npm run build --prefix src/main/frontend
npm run dev --prefix src/main/frontend
```

`npm test` выполняет локальные selfcheck логики и рендеринга; это не браузерные end-to-end тесты. Java-тесты работают без контейнера Jira. Проверку реальной AO, Scheduler, OSGi, внешних каналов и нескольких нод DC нужно выполнять отдельно.

### Где искать код

| Путь | Назначение |
|---|---|
| `src/main/java/ru/my/api` | Интерфейсы сервисов |
| `src/main/java/ru/my/impl` | Listener, очередь, отбор получателей и каналы |
| `src/main/java/ru/my/ao` | Схема хранилища Active Objects |
| `src/main/java/ru/my/model` | Модели событий, настроек и подтверждений доставки |
| `src/main/java/ru/my/rest` | REST API пользователя и администратора |
| `src/main/frontend/src` | React-интерфейс настроек |
| `src/main/resources/atlassian-plugin.xml` | Модули плагина, AO-сущности и web resources |
| `src/test/java` | Java unit-тесты |

Компоненты регистрируются Atlassian Spring Scanner; платформенные сервисы импортируются через `@ComponentImport`. JS/CSS подключаются через web resources в descriptor.

**Не меняйте `groupId`, `artifactId` и ключ `ru.noname.atlassian.jira.in`.** От ключа зависит префикс таблиц AO; изменение оставит существующие данные под прежним префиксом. При обновлении сохраняйте Jira home и БД: настройки, ожидающая очередь и журнал подтверждений находятся в AO.

### REST API

Базовый путь: `<jira-context>/rest/issue-notifier/1`.

- Пользователь: `/user/settings`, `/user/delegation`, `/projects`, `/users`.
- Администратор: `/admin/settings`, `/admin/settings/test`, `/admin/contexts`, `/admin/failed-notifications`.

Для сохранения контекстов клиент должен получить ETag из GET и передать его в `If-Match` при PUT. Отсутствующий заголовок даёт 428, конфликт — 409. Успешный PUT возвращает сохранённый список и новый ETag. Для ошибок отправки используется курсор `beforeId`, до 50 проверяемых записей на страницу.

Ручной повтор: POST `/admin/failed-notifications/{id}/retry` (администратор с доступом к задаче и комментарию). Ответ 202 означает постановку на ближайшую обработку, 404 — событие недоступно или уже обработано, 409 — занята блокировка обработки. Блокировки распределены по 64 группам, поэтому конфликт возможен и при обработке другого события той же группы.

### Гарантия приёма и карантин

Повторная доставка гарантируется только для события, успешно записанного в AO. Ошибка разбора исходного Jira-события или отказ БД до записи не создают задание: событие не восстанавливается автоматически. На вкладке ошибок показаны число ошибок приёма, время и безопасное описание последнего сбоя. Счётчик хранится в памяти текущего экземпляра плагина, сбрасывается при перезапуске/перезагрузке плагина и не является общим для нод DC. Для расследования используйте также логи; смена обслуживающей ноды может показать другой счётчик. API: GET `/admin/intake-diagnostics` (только администратор).

Нечитаемые сохранённые события и журналы подтверждений переходят в карантин. Автоматические и ручные повторы для них остановлены; сетевые ошибки и временные ошибки каналов по-прежнему повторяются. Записи карантина остаются на вкладке ошибок. Администратор может удалить такую запись с подтверждением; неотправленные уведомления при этом будут потеряны. API: POST `/admin/failed-notifications/{id}/discard`, доступен только для карантина и с проверкой прав задачи/комментария. Для нечитаемых метаданных администратору разрешено удалить запись без раскрытия её содержимого.

Карантин использует новое nullable-поле AO `QuarantinedAt`: существующие записи продолжают обработку, таблицы и ключ плагина сохраняются. Реальную миграцию схемы при обновлении нужно проверить в Jira.

Глобальная конфигурация сохраняется атомарно. Отправка Mattermost использует один согласованный снимок URL, токена и bot ID на поиск пользователя/канала и отправку сообщения, включая ключи кеша. Изменение конфигурации влияет на следующие отправки. GET настроек и проверочная отправка также используют согласованный снимок. Если настройки изменились между серверной проверкой и сохранением формы, PUT возвращает 409: обновите страницу и повторите сохранение.
